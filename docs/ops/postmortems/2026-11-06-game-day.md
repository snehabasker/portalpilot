# 2026-11-06: Game day (portal outage, worker loss)

* Severity: one ticket (PortalDegraded), one page (NoWorkers) · Author: Sneha Basker · Status: reviewed
* Environment: local docker compose stack with the `ops` profile (Prometheus, Alertmanager, Grafana, outbox relay),
  mock portal, chain `cache,dom`, 1 worker with 4 browser sessions, batches of 8 rows at concurrency 3
* Driver: [`e2e/game_day.py`](../../../e2e/game_day.py). Raw record (timeline, incident timelines, checks):
  [`e2e/results/game_day_run1.json`](../../../e2e/results/game_day_run1.json) (the run this document is about) and
  [`e2e/results/game_day.json`](../../../e2e/results/game_day.json) (the verification run after the fixes, 21:40 UTC)

This was a **planned exercise**: both failures were injected on purpose. It is written up like a real incident,
because the point of a game day is to find out what a real one would be like.

## Summary

Two failures were injected into a running system. **(A)** The client portal returned 503 on 85 % of page loads
for about 8 minutes while a batch ran. **(B)** The only browser worker was killed with no grace period mid-batch.
Both were detected by the new SLO and alerting stack, became incidents in the Studio, were acknowledged and
resolved, and every valid claim was filed **exactly once**. Two real weaknesses surfaced: the portal outage was
detected **6 min 43 s** after it began, although tasks were already stuck within about a minute; and tasks waiting
on a human **blocked the rest of the batch**. Fixing detection then exposed two monitoring bugs (contributing
factors 5 and 6). After the fixes, a verification run detected the same outage in **1 min 47 s** and passed every
check: 16 claims for 16 clicks, 16 of 16 tasks succeeded.

## Impact

* No duplicate claims: portal references were all unique, submit clicks equalled claims on the portal (14/14 in
  run 1), and `portalpilot_double_submit_suspects` stayed at 0.
* Scenario A: 3 of 8 tasks were handed to a human. The other 4 valid rows **did not start until those 3 were
  handed back**, although the portal had recovered (contributing factor 2).
* Scenario B: all in-flight work paused for about 3.5 minutes, then resumed on the restarted worker with no
  intervention beyond the restart.
* Test data, not the system: one row per batch was rejected at onboarding (`unknown loss type 'Storm'`), and in a
  rerun 4 rows used policy numbers the mock portal treats as unknown (`POL-9xxxxx`, by design). Onboarding and the
  agent behaved correctly in both cases: they rejected the row and never submitted. The generator was fixed; the
  verification run has no such rows.

## Detection

| | Injected → alert firing | → incident in Studio | Was that good enough? |
|---|---|---|---|
| Portal outage | 5 min 58 s | 6 min 43 s | **No.** Tasks were stuck in about a minute, and by the time anyone was told, the whole batch had stopped. |
| Worker loss | 3 min 07 s | 3 min 22 s | Yes for a page: it matches the alert's `for: 3m`, which is there to ride out a rolling deploy. |

`PortalDegraded` is a *ratio over a 10-minute window*, held for 5 minutes. It was designed not to fire on a short
blip. But in an outage the agent stops generating stage attempts as soon as tasks park on humans, so the signal
weakens just as the problem gets worse. The leading signal was different: **`unexpected_page` interventions opening
in a burst.**

## Response and recovery

The runbooks were followed as written and were enough to recover both cases. Two things slowed the response:

* The operator had to hand back every stuck task **one at a time**. That is three clicks here; on a 400-row batch it
  would be dozens.
* In A, nothing in the Studio said *why* 4 rows were still `queued` after the portal recovered.

## Follow-up: fixing detection found two more bugs

Action item 2 added `StuckTasksBurst` (≥ 3 tasks handed to a human in 5 min). Re-running the game day:

* **Run 2: the new alert did not fire.** All three stuck tasks opened their interventions between two scrapes.
  The labelled counter `portalpilot_interventions_opened_total{kind="unexpected_page"}` did not exist until its
  first increment, so Prometheus first saw it already at 3, and `increase()` reads a new series as no change. The
  fix is the standard one: create every known label value at 0 when the process starts. There is a unit test for it.
* **Run 3: `PortalDegraded` never fired at all.** Every task parked within a minute (3 waiting on a human, 5 queued
  behind them because of factor 2), so stage attempts stopped completely, and a ratio of attempts has nothing to
  measure. This is factor 1 at its extreme. It is why the leading alert must count *stuck tasks*, not portal errors.
* **Verification run (21:40 UTC)**, with both fixes deployed:

| | Injected | Alert firing | Incident in Studio | Acked | Recovered |
|---|---|---|---|---|---|
| Portal outage (`StuckTasksBurst`) | 20:40:05 | 20:41:07 (**1 m 02 s**) | 20:41:52 (**1 m 47 s**) | 20:41:53 | batch done 20:43:43, 8/8 |
| Worker loss (`NoWorkers`) | 20:43:45 | 20:46:57 (3 m 12 s) | 20:47:12 (3 m 27 s) | 20:47:18 | batch done 20:48:00, 8/8 |

  All checks passed: no reference filed twice, 16 claims for 16 clicks, double-submit suspects 0, every task

## Contributing factors

1. **Detection relies on a rate that the failure itself suppresses** (above).
2. **Parked tasks hold concurrency slots.** `BatchWorkflow` counts a child as running for its whole life, including
   while it waits on a human. With concurrency 3 and 3 parked tasks, the batch stalls. This is a design flaw that
   unit tests did not catch, because they test one task at a time; only a batch-level failure revealed it.
3. **Recovery is per task.** There is no batch-level "portal is back: retry all stuck tasks at stage X".
4. Alertmanager delivers resolutions after `group_interval` (5 min), so the auto-resolve event in the timeline lags
   the real end. The incident's `resolved_at` uses the alert's `endsAt` and is correct; only the timeline event is late.
5. **Lazily created labelled counters hide bursts** from `increase()`/`rate()` (follow-up, run 2).
6. **The rule unit tests could not catch either monitoring bug.** promtool tests start from a series that already
   exists, and they model traffic that continues during an outage. Only the live game day showed the first scrape of
   a new series and the stage attempts stopping. Game days test the alerting, not just the system.

## What went well

* **Correctness held under both failures**: zero duplicates, with every submit accounted for. The four layers in
  ADR 0003 and the session-affinity recovery in ADR 0004 behaved as designed.
* The whole alert path worked end to end the first time: rule → Alertmanager → Studio incident → outbox → event
  bus. Acknowledging in the Studio took under 10 s.
* The worker loss needed no human action beyond restarting the process. Nothing had to be repaired by hand.
* The incident timeline captured the diagnosis note at the moment it was made, so this document was written from
  records rather than memory.
